---
name: worktree
description: "Create a git worktree branched from the current branch and confine the rest of the session's work to it. Use when the user explicitly says 'worktree' — 'start a worktree', 'work in a worktree', 'create a worktree', 'isolate this in a worktree'."
---

1. **Read the branch point.** Run `git rev-parse --abbrev-ref HEAD` for the current branch (or the commit SHA on detached HEAD). If `git status --porcelain` shows uncommitted changes, say plainly that the worktree starts clean from the last commit — those changes stay behind in this checkout — and resolve it via an interactive prompt: **continue** (leave them behind, proceed as-is); **commit first** (run the normal commit-confirmation flow — proposed message, staged files, explicit yes — before continuing); or **stash** (`git stash` here now, then `git stash pop` inside the new worktree right after Step 3 succeeds — stash entries are shared across worktrees of the same repo, so this carries the work over instead of stranding it).

2. **Name the new branch and its worktree path.** The current branch stays checked out here, so the worktree needs its own new branch. Look for an issue number or other ID in the request that triggered this skill, or the session's linked tracker item/ticket if one exists; if found, derive the branch name from it directly — no prompt. Otherwise propose a default (`<current-branch>-worktree`, or a generic fallback like `worktree` on detached HEAD) and confirm or let the user edit it via an interactive prompt. Before creating anything, run `git branch --list <new-branch>`: if it already exists, check `git worktree list` for a worktree already using it and offer to switch into that one instead of duplicating it; if no worktree uses it, ask for a different name via an interactive prompt rather than reusing a stale branch silently. Build the worktree path as a sibling directory of the repo root — `../<repo-dir-name>-<new-branch>`, replacing `/` and other path-unsafe characters with `-` in the *path segment only* (the branch name itself keeps them) — never nested inside the repo, since a target repo's `.gitignore` may not exclude it. If that path already exists for a different branch, ask for a different name rather than overwriting it.

3. **Create it.** Run `git worktree add <path> -b <new-branch> <branch-point>`. Done when `git worktree list` shows the new path and `git -C <path> rev-parse --abbrev-ref HEAD` reports the new branch. If it fails partway (branch created but the checkout didn't complete), clean up with `git branch -D <new-branch>` before retrying — never leave an orphaned branch behind.

4. **Confine the session to it.** Treat `<path>` as the working root for everything that follows: run Bash commands from inside it, and use absolute paths under it for every Read/Write/Edit/Glob/Grep call. State the new working root back to the user once. This holds for the rest of the session — a request to touch something outside the worktree (the original checkout, another path) is a one-off exception for that request, not a standing one.

5. **Stop there.** Setting up and confining to the worktree is this skill's whole job. Do not start implementing, editing project files, or otherwise advancing the task on your own initiative once Step 4 is done — wait for the user's next explicit instruction before touching anything beyond what Steps 1-4 required.

Pairs with `wrap-up`'s worktree-cleanup step, which detects a worktree session and handles merging the branch back and tearing the worktree down at the end — this skill only covers the start.
